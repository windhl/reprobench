# 从已读论文归纳 empirical study 的写法

日期：2026-11-19。用途：回应作者对实证研究行文方式的讨论，为 ReproBench 大纲 v2 提供依据。下面区分原作做法与针对本工作的建议；这些是写作判断，不是会议规定。

## 1. 实证论文的中心是什么

在这些论文中，文章主要交付的是对一个实际现象的可信认识：研究什么现象，现有知识缺在哪里，如何观察和检验，观察到了哪些可重复核查的规律，这些规律在什么范围内成立。

可以把全文逻辑概括为：

**实际问题 → 尚不清楚的问题 → 研究设计与判定依据 → 观察结果 → 有依据的解释 → 适用范围与含义。**

任务集、执行框架和评价方法使研究成为可能；贡献的组织仍应回到“我们因此知道了什么”。成功率、模型比较和资源发布可以保留，但每项分析都需要服务于研究问题。取消加权打分后，结果判定、行为编码和有效性检查仍然需要清晰的方法。

## 2. 论文实例：它们怎样推进论证

以下概括的是原作的论证路径，不声称各篇都使用同一套章节名称。阅读范围与版本见[逐篇笔记](reading-notes.md)和[来源记录](../sources.json)。

| 论文 | 原作的推进路径 | 对我们的启发 | 借鉴的边界 |
| --- | --- | --- | --- |
| [Crowd-reported Vulnerability Reproducibility, USENIX Security 2018](https://www.usenix.org/conference/usenixsecurity18/presentation/mu) | 先定义人工复现流程与资料条件，测量可复现性，再分析信息汇总、排障及专家经验 | 将复现拆成有证据的实际活动；将“缺少什么”与“什么缺失妨碍复现”分开讨论 | 不能把某信息缺失的频率直接解释为它的因果重要性；其人工、源码、崩溃判定条件与我们不同 |
| [Web PoC Generation Study, arXiv:2510.10148](https://arxiv.org/abs/2510.10148) | 基础生成表现 → 失败分解 → 上下文条件比较 → 反馈与提示策略实验 | 研究问题可以递进，后一个分析针对前一个留下的解释缺口 | 环境已准备；后两步有实际干预实验，我们尚未做时不能借用其因果力度 |
| [Enterprise Networks, TOSEM 2026](https://doi.org/10.1145/3766895) | 方法与 prototype → 定量 evaluation → 在 discussion 中结合专家轨迹分析解释行为 | 全局统计与局部轨迹各有作用：统计说明范围，轨迹展示过程 | 它同时提出系统；不能照搬为我们的新 agent 架构贡献，也不能声称模型内部机制已被直接观察 |
| [From Capabilities to Performance, EMNLP 2025](https://aclanthology.org/2025.emnlp-main.802/) | 功能属性与任务表现 → 失败模式 → 架构干预 → 回看能力与表现的关系 | Discussion 可以把多个结果连成更高层解释，而不只是重复数字 | 作者的功能解释与人类干预须保留条件；“记忆差”“推理弱”需要具体证据 |
| [Local Privilege Escalation Interventions, arXiv:2604.27143v2；作者注明 RAISE workshop 录用](https://arxiv.org/abs/2604.27143) | 方法 → 已识别失败模式 → 候选增强 → prototype → 实验比较 | 如果决定验证改进，增强应从观察到的问题推导，并以实验检查 | “提出修复方案并证明有效”是额外贡献，不是每篇实证研究的必要章节 |
| [Decoupling Reconnaissance and Exploitation, arXiv:2606.25332](https://arxiv.org/abs/2606.25332) | 指出早期失败遮蔽后续能力 → 设计阶段解耦与前提信息注入 → 比较结果 | 若想说明环境准备掩盖了漏洞触发能力，需要提供前提的对照来加强解释 | 仅比较自然运行中进入不同阶段的样本，不能获得同样的结论 |
| [Incalmo, IEEE S&P 2026](https://doi.org/10.1109/SP63933.2026.00132) | 基线失败分析 → 设计高层任务接口与执行服务 → 系统评估 | 是“研究发现驱动新系统”的另一种组织方式，可用作对照 | 我们目前的主要目标是认识现象；没有对应系统贡献时不需设置系统设计章 |

这些例子至少包含三条不同路线：

1. **描述与诊断。** 刻画结果、条件和行为，提出有边界的解释。适合现有 ReproBench 数据的基础版本。
2. **观察后检验。** 在发现疑点后改变某项条件，测试解释或改进是否成立。适合后续少量针对性补充实验。
3. **观察驱动系统设计。** 从失败归纳设计需求，再提出并评估新系统。需要真实的新系统和对应证据。

这三条路线可以组合，但文章应让读者知道哪些结论来自观察、哪些来自干预。正式发表的系统论文与预印本也不能被笼统地当作“纯实证论文模板”。

## 3. 常见框架及各部分承担的任务

### Introduction：为什么这个问题值得知道

从具体实践问题切入，说明它为何重要；准确指出现有研究已覆盖什么、哪些情形仍缺少证据；提出可回答的问题；介绍研究范围、主要发现和贡献。

好的 gap 是一个缺乏可靠答案的具体问题。例如，已准备好环境中的 PoC 生成结果，能否说明 agent 能从 CVE 标识完成固件目标准备？也要承认已有自动重建研究，再说明任务对象、起点和研究重点的差别。仅说“缺少 IoT benchmark”不足以支撑本稿的实证定位。

### Background / Task Definition：让读者能理解观察对象

只解释理解任务和结果需要的知识。为“复现成功”“运行真实目标”“模拟漏洞逻辑”等容易混淆的概念建立共同语言。细致的判定流程放 Methods；文献群之间的完整比较放 Related Work。

### Study Design / Methodology：为什么可以相信后面的事实

回答：研究问题是什么；为何选这些样本；实际执行条件是什么；收集到了哪些证据；怎样定义结果和分类行为；谁判定、如何处理分歧；缺失数据和统计单位怎样处理。

每个 RQ 应能回指具体数据和分析方法。方法细节不应只列工具名称，还要解释关键选择如何影响结论。使用定量和定性材料时说明两者如何配合，不必为了形式把研究包装成已实施的 grounded theory 或正式混合方法设计。

### Results / Empirical Study：逐步回答问题

可以用一章包含多个 RQ，也可以分别设章；两种方式都有实例。选择依据是分析的复杂度、是否存在独立实验，以及篇幅。

对于共享同一批运行和判定体系的我们，当前建议统一为一章，按三个 RQ 组织。重点是分析之间的连接：先知道做成了什么，才能解释未完成的情况；再看遇到这些情况时 agent 如何行动。

### Discussion：把发现连起来，说明认识发生了什么变化

结果小节可以作贴近证据的解释。Discussion 则跨越多个结果，回答：这些发现共同说明什么；修正了什么原有预期；对使用者或研究者有什么具体影响；哪些解释仍待测试。

例如，“许多运行停在环境准备”属于结果；“因此未观察到后续利用成功，不能断言模型缺乏对应构造能力”属于解释边界；“需要将目标准备和目标上的漏洞触发分别报告”属于由此支持的评价建议。

### Threats to Validity：结论可能怎样被误读或偏移

将威胁与具体结论关联，并说明已采取的措施及剩余限制。包括判定是否正确、执行条件是否混淆、样本能否推广、重复次数与聚类是否支持比较。

这一节可以独立，也可以合并；当前建议独立，避免与科学含义混杂。它不承担为全部研究缺陷辩护的任务。

### Related Work 与 Conclusion

Related Work 按研究问题和任务条件比较，说明我们的证据补充了哪一块。关键先行研究仍需在 Introduction 及时交代；放在后面的完整综述不能替代前面的研究定位。

Conclusion 回答中心问题，重述经核查的认识和意义。资源名称可以出现，不新增结果或放大总体能力主张。

## 4. 每个研究问题怎样写成一段完整论证

推荐顺序如下，不要求每项都成为小标题：

1. **动机。** 为什么需要这个分析，它接着前一个问题解决什么疑点？
2. **局部方法。** 调用哪个样本子集、怎样计数、分母是什么；共享方法引用 §3，避免重复。
3. **总体观察。** 给出主要分布、差异和不确定性，先写能直接被图表或证据检查的事实。
4. **过程证据。** 用有代表性的轨迹解释现象，并报告是否存在反例和替代路径。
5. **解释与边界。** 哪种解释得到支持，哪些仍只是可能原因？配置、采集或样本差异是否也能解释？
6. **明确回答。** 用短段落回答该 RQ，并自然引出下一个分析。

案例最好紧邻相应统计。展示时间线时把命令、反馈、下一步行动和后续产物连起来；只摘取一段 agent 自述，难以支持行为过程的结论。反例能帮助说明边界，例如同样缺失某依赖，有的运行修复后继续，有的转向模拟。

## 5. 从 observation 到 finding 再到 insight

| 层次 | 含义 | 对本工作的示例写法，均须实际验证 |
| --- | --- | --- |
| Observation | 可直接核查的事实 | 某次运行因缺少加载器未能启动目标，随后生成了重新实现服务的代码 |
| Finding | 多条证据支持的规律或差异 | 在已核验的环境启动受阻事件中，某类响应较常出现；明确事件数、运行数和反例 |
| Insight | 对发现意义的有边界解释 | 对这类任务，仅有“生成了可执行 PoC”的产物不足以反映真实目标上的进展，需同时检查目标身份与执行证据 |
| 待检验解释 | 与现象相容，但尚缺鉴别证据 | 明确允许失败报告是否会减少模拟替代；提供就绪环境是否会改变后续触发表现 |

上表是证据层级的示范，不是已经成立的 ReproBench 发现。不能把“出现模拟”写成“因奖励而作弊”，也不能把一个运行的依赖报错扩展为“环境是所有模型能力的首要决定因素”。日志有时足以确认具体执行失败的直接原因，但跨案例的因果重要性需要更强证据。

## 6. 应用于 ReproBench 的主线

建议采用“描述与诊断”为主、允许后续检验的路线：

**从 CVE 标识开始，agent 在真实目标上取得什么结果 → 哪些条件未满足、实际执行在哪里受阻 → agent 如何处理这些障碍，以及继续行动和最终表述是否仍对应真实目标。**

六类工作活动给过程定位；结果判定提供可信终点；轨迹分析解释执行与应对。这些材料共同回答研究问题。环境问题和模拟行为在同一条执行过程中承担不同分析角色，可以同时深入研究。

模型差异作为各 RQ 的比较维度，无需另设“模型排行榜”主线。模拟也不预先定义为全部失败的共同机制：明确声明的模拟、未完成复现以及证据不足的成功声明应分别记录。

30 个 CVE 可以支撑对所选情形的深入研究，前提是研究范围清楚、证据有深度、发现对理解问题有价值。改为实证研究仍需要处理选择偏差和代表性；450 次运行主要增加重复和配置比较，不能等同于 450 个不同漏洞。

## 7. 写作时可直接使用的检查问题

- Introduction 最后能否清楚说出“研究后多知道了什么”？
- 每个 RQ 是否对应实际可获得的数据与可完成的分析？
- 每个重要数字能否回溯到同一条运行的证据和明确分母？
- 每个行为解释是否有轨迹、跨案例支持、反例或替代解释？
- Discussion 是否增加跨结果的理解，而不仅复述最高成功率？
- 是否把具体 agent 配置上的表现写成了模型普遍、内在的能力？
- 是否将未实施的标注、对照或补充实验写成了既成事实？
