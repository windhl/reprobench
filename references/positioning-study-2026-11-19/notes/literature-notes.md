# 逐篇阅读笔记

“对我们的启发”均为本次分析，不是原论文的自述。规模不可跨任务直接比较：固件镜像、CVE、训练靶机、子任务和重复运行是不同单位。外文原文请查同名 `../papers/*.pdf`、`../texts/*.txt`。

## 1. CVE-Bench：小规模 benchmark 依靠什么成立

- 来源：[ICML 2025 正式页面](https://proceedings.mlr.press/v267/zhu25i.html)；本地 PDF 是 arXiv:2503.17332v4。
- 核读：§1、§3 全部、§4、§5，重点 §3.3、§4.3；正文逻辑页 1–9。
- 40 个 CVE；每个实例有目标容器、参考利用和自动判定。限定为特定时间窗内的关键级 Web 漏洞，排除了不能复现的案例。
- 贡献重心是可交付的 sandbox 与任务规范；八类攻击目标使多种 agent 行为可被统一判定。三种 agent 框架、zero-/one-day 设置、单次和多次尝试结果支撑其用途。
- 失败分析由两位作者独立标注所有运行，再讨论分歧。它本身也做实证分析，因此两种定位并非互斥。
- 注意：论文允许达到标准攻击目标，而不总是精确证明触发指定 CVE，文中就有利用其他漏洞的案例。不能把这类成功率直接与严格指定漏洞复现率比较。
- 对我们：30 与 40 的差异不是最关键的差异；参考复现、可执行判定和第三方可用性才是必须对齐的交付标准。

## 2. Cybench：任务质量、可验证性和接口

- 来源：[ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/hash/3e9412a9c1d93810ef3ef7825115016b-Abstract-Conference.html)。
- 核读：§1–2、§3.3、§4、§5、§7；正文逻辑页 1–10。未逐页阅读后续全部任务日志。
- 40 个专业 CTF 任务；首解时间提供难度参照；每项加入解题脚本，并用 CI 和服务探测验证可构建、可求解。
- 将 unguided 成功、subtask-guided 成功、子任务完成比例分开报告，不把部分进度混成一个终局成功指标。比较八个模型和四种 scaffold。
- 论文对 scaffold 效果的发现依赖模型；增加 web search 或交互能力并不对所有模型都有益。
- 对我们：六阶段可用作分析结构，但应区分自然运行和人为提供阶段提示的设置；阶段分数不必靠任意权重合成“模型能力”。benchmark 的核心还包括他人可以接入的接口和任务验证。

## 3. BountyBench：40 个漏洞也可以具有强 benchmark 贡献

- 来源：[作者项目页](https://bountybench.github.io/)；本地是 NeurIPS 2025 Datasets and Benchmarks 论文。
- 核读：正文 §1–7；另读附录 L 的实验统计设计，以及 Detect/Exploit/Patch 验证相关段落。未精读全部 120 页日志。
- 25 个系统、40 个 bounty，展开为 120 个 Detect/Exploit/Patch 任务；两种单位不应混用。
- 重点是系统快照、真实运行环境、参考利用、补丁、code/runtime invariants，以及区分漏洞的判定机制。作者交叉审查构建工作，并用 CI 验证。
- 通过逐步增加漏洞信息调节任务难度，说明一个小型实例集可以支持多个有明确含义的实验条件。
- 附录讨论任务/仓库差异和重复尝试的统计不确定性，不能将多次尝试简单视为独立漏洞。
- 对我们：有启发的是固定对象下控制信息量与环境条件。发布数据与实证发现可以并存；前者若作为主贡献，需能被外部用户可靠使用。

## 4. SEC-bench：规模背后的构建方法

- 来源：[官方代码与数据入口](https://github.com/SEC-bench/SEC-bench)；本地为 NeurIPS 2025 论文。
- 核读：§1–2 全部、§3.1–3.3、§5–6；任务定义、人工验证与失败分析为重点。
- 898 个候选中验证出 200 个实例；三类专门 agent 负责构建、PoC 和补丁，sanitizer 构成可执行 oracle。完整实验和部分模型比较使用的子集不同。
- 两名有安全工程经验的作者检查报告和补丁，并清理可能直接泄露补丁的输入。自动构建并不等于完全不需人工质量控制。
- 核心贡献包括可扩展的构建方法，而不只是 200 这个数字；同时存在模型/agent 比较和失败归因。
- 对我们：不宜为了样本量单独对标。若坚持 benchmark，需要解释固件任务为何难以批量构建，以及保留下来的案例如何验证；不能用 LLM 读取公开材料代替真实参考复现。

## 5. Patch-to-PoC / K-Repro：最接近的实证研究参照

- 来源：[arXiv:2602.07287v2](https://arxiv.org/abs/2602.07287)。本地旧名 `k-repro.pdf` 容易掩盖它的实际定位。
- 核读：正文 §1–7、§9，特别是 §3.1、§4.3–4.6、§5.2–5.5、§7；逻辑页 1–13。
- 100 个 KernelCTF 漏洞；以 patch commit 为输入；确定性流程准备内核环境，agent 使用源码浏览、VM 和调试工具。
- 研究问题覆盖效果、效率、稳定性、输入/工具影响；分析漏洞类型时控制 race condition 这个混淆因素。
- GDB 使用普遍，但移除后总成功率几乎不变；移除 commit message 的影响更明显。这是“频繁使用”与“边际帮助”不同的直接例子。
- 识别通过调试器直接修改执行状态制造的人工崩溃，并将其判为失败；但其自动成功判断与指定根因的等价性仍有局限。
- 对我们：最值得借鉴的是受控实验如何支持瓶颈判断。原作也提出新研究系统，不能把它当作“只改标题即可成立”的例子，更不能将其成功率直接与仅 CVE 输入的 IoT 任务比较。

## 6. One-day Vulnerabilities：能力研究也使用 benchmark 一词

- 来源：[arXiv:2404.08144v2](https://arxiv.org/abs/2404.08144)，预印本。
- 核读：正文 §1–8，重点 §3、§5–6；逻辑页 1–10。
- 15 个案例，包含 14 个 CVE 来源漏洞和 ACIDRain；十个模型，人工判断利用是否成功，区分 pass@5 与逐次成功率。
- 去掉 CVE 描述后，GPT-4 的 pass@5 从约 87% 降到约 7%，支持“提供的信息改变任务难度”，而不仅是给一个模型排名。
- 公开版本未给出完整 prompt；人力成本为估算。选择可复现案例、样本小和当时模型能力限制都需要纳入解释。
- 对我们：同一篇文章可以构建 benchmark 作为研究工具，但把能力边界作为主要结论。小规模预印本能展示这种叙事，不构成 USENIX 录用门槛的证据。

## 7. LLMs as Hackers：研究平台与实证主线能够共存

- 来源：[Empirical Software Engineering 正式页面](https://link.springer.com/article/10.1007/s10664-025-10758-3)，实际发表于 2026-02-10，31:70。DOI 中的 2025 不代表出版年份。
- 核读：§1.2–1.3、§3.5、§4、§5 中指导与上下文实验、§6 定性分析和有效性威胁；其他系统背景为补充阅读。
- 12 个受控提权测试案例，主要是配置漏洞，不是 12 个野外 CVE；发布测试平台、agent 和轨迹。
- 研究问题同时包含成功率、与人工/传统工具的比较、上下文策略和指导机制。定性分析细化到忽略错误、重复命令和有时间依赖的多步利用。
- 对我们：它直接说明“发布 benchmark”可以服务于实证研究。但小型受控测试平台的结论边界，与声称代表真实 IoT 漏洞总体不同；不要只引用案例数量为自己背书。

## 8. Uncovering the Limits：安全顶会中的测量有效性贡献

- 来源：[USENIX Security 2024](https://www.usenix.org/conference/usenixsecurity24/presentation/risse)。
- 核读：§1、§3、§4 中数据/模型设计、§5 的对照结果、§6–7。
- 六种学习式检测技术；采用语义保持变换，以及漏洞/补丁配对测试，检查通常的高分是否意味着学到了漏洞相关信息。
- 核心不是“模型不够好”，而是设计能区分不同解释的测试，并证明常规评估遗漏的问题。论文也交付新的数据与评估方法。
- 对我们：模拟服务与真实固件目标之间的差别，有机会形成类似的测量有效性问题。但必须展示哪些声明会被何种判定方式误认，以及证据验证如何纠正；不能推定全部已有 benchmark 都会误判模拟服务。
- 限制：它研究函数级检测，并非 agent 固件复现；可借鉴论证逻辑，不应当作直接任务性能对照。

## 9. Local Open-Weight：最新且直接相关的探索性实证研究

- 来源：[arXiv:2611.06257v1](https://arxiv.org/abs/2611.06257)。作者明确标注为 JSS 在审预印本。
- 核读：正文 §1–6，重点 §3、§4.2–4.4 和 §5 的局限；未逐项核查其公开 artifact。
- 十个 CyberGym 任务、十二种本地配置、每种三次，共 360 次运行。控制 harness 和 serving stack；在明确限定的任务集上比较配置，避免声称给出整个 benchmark 的总体分数。
- 分析推理假设正确但输入文件格式错误、盲目重复与检查自身产物等过程；也讨论吞吐量与固定时间预算的混淆。
- 深入轨迹例证集中于 GraphicsMagick；更广泛的失败机制仍需系统验证。“量化不改变能力”等宽泛说法不能超出其小型配对比较。
- 对我们：小规模研究可以把预算用于配置和轨迹深度，同时明确外推边界；其参考文献 [17] 已引用 ReproBench。此处引用只证明存在关联研究，不代表认可全部结论或审稿通过。

## 10. PentestGPT：解释问题后提出系统的混合路线

- 来源：[USENIX Security 2024](https://www.usenix.org/conference/usenixsecurity24/presentation/deng)。
- 核读：§3 benchmark 构建、§4 exploratory study、§5 设计依据及摘要/结论。
- 13 个靶机、182 个子任务；专家验证 walkthrough。探索研究分析上下文丢失、近期任务偏好和错误操作，再用这些发现指导系统模块设计。
- 原文实验包含专家执行和反馈的交互过程；不能作为与完全自主运行直接等价的结果。
- 对我们：13 个机器不是“13 个 CVE 的纯实证研究被录用”的证明，它包含系统贡献。若走此混合路线，需要有针对发现的设计与验证；目前不必为了投稿而临时把 ReproBench 扩成新 agent。

## 11. FirmAgent：IoT 卡点应落到可观测系统约束

- 来源：[NDSS 2026](https://www.ndss-symposium.org/ndss-paper/firmagent-leveraging-fuzzing-to-assist-llm-agents-with-iot-firmware-vulnerability-discovery/)。
- 核读：§I–III、§VI 中 PoC 有效性、§VII 重托管局限；实现和其他实验为补充核读。
- 以小规模固件实证观察 source/sink 可达性差异，进而提出 fuzzing＋LLM 分析系统；评估涉及 14 份固件。
- 明确要求目标服务可被单服务重托管，并说明重托管失败、单二进制范围的限制。它是在已满足部分执行前提的目标上研究发现能力。
- 对我们：可比较真实工作流前提与固件环境约束，但不能把 14 份固件等同于 14 个漏洞来论证样本量足够。更有价值的是把 NVRAM、依赖、路径可达性转成可验证事实，而非笼统称为领域知识不足。

## 12. CVE-GENIE：必须正面比较的环境重建工作

- 来源：[arXiv:2509.01835v2](https://arxiv.org/abs/2509.01835)。
- 核读：§1–3 的任务与环境准备、§4 的实验设计及大规模分析、验证器示例和局限；未精读所有 prompt 附录。
- 从 CVE 条目定位资源与源码，构建环境，生成利用与 verifier；在 841 个 CVE 上报告 428 个复现。数据处理明显面向可获取的项目源码，与二进制固件重托管不能混为一谈。
- 采用模块消融、信息缺失测试，并人工分析部分成功与失败案例。它的重点是新系统和可生成复现数据的流程。
- 对我们：已存在把环境重建纳入自动化的工作，不能继续做“首次研究所有 pre-environment 复现”的宽泛主张。应区别专门构建的复现系统与通用 coding agent，源码重建与固件运行约束，并以同口径实验决定是否适合做直接基线。
