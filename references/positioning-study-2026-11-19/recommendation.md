# ReproBench 的论文定位判断

这是 2026-11-19 文献调研后的研究判断，尚未进行新增 agent 实验，也未替作者决定最终题目。材料索引和阅读范围见 [README](README.md)，具体来源见 [逐篇笔记](notes/literature-notes.md)。

## 判断：实证研究作为主线，ReproBench 作为支撑研究的开放资源

我倾向转向 empirical study。决定因素是现有材料最有价值的部分：30 个固件漏洞上的重复运行、六阶段轨迹、真实目标证据，以及 agent 在环境重建中发生的具体行为。它们更直接支撑“实际发生了什么、哪些约束与结果有关”的研究。

但我不完全赞同“数量不够，所以 benchmark 不成立”这条理由。CVE-Bench 和 Cybench 都以 40 个实例为核心；BountyBench 是 40 个 bounty、25 个系统。小型安全 benchmark 的成立依靠高质量任务、可靠 oracle、可接入的评估协议和外部复用价值。30 个精心验证的 IoT 案例也并非天然不够；现有材料是否满足这些交付要求才是关键。

benchmark 和 empirical study 并非会议里互斥的正式投稿类型。区别主要在贡献的重心与作者对读者作出的承诺：

| 问题 | benchmark 为主 | 实证研究为主 |
| --- | --- | --- |
| 核心承诺 | 他人能据此可靠评测新工具 | 结论有证据支持，并说明适用范围 |
| 主要贡献 | 任务、环境、oracle、接口、覆盖和维护方法 | 研究问题、观察、对照、解释及可行动的发现 |
| 案例选择 | 对预期评估用途有覆盖、区分度和稳定性 | 对研究问题有信息量，选择过程透明 |
| 六阶段的角色 | 要验证测量是否有效、稳定、公平 | 用作过程编码和分析框架，同样需标注可靠性 |
| 总分/排名 | 需要证明它适合比较工具 | 可以弱化，优先报告真实结果和过程 |
| 主要风险 | 外部用户无法复用，分数不代表目标能力 | 把局部观察说成总体规律，把相关说成因果 |

## 这次调研改变了哪些判断

第一，重构叙事有充分理由，但它不会自动修复旧评审指出的问题。样本选择、judge 稳定性、参考正确性和早期失败混淆，在实证研究中仍然是有效性问题。

第二，研究不必强行新增一个 agent 系统才有价值。USENIX 的 Uncovering the Limits 展示了评估方法与实证发现的贡献空间。不过 Patch-to-PoC、PentestGPT、FirmAgent 都包含研究系统，不能只截取它们的案例数或 failure analysis 来推定目前稿件已达到相同贡献强度。最新 Local Open-Weight 是直接相关的实证预印本，但仍在审。

第三，应收窄既有工作的概括。CVE-GENIE 已从 CVE 条目重建环境并生成可验证利用；Patch-to-PoC 的框架也会自动准备内核。差异应落到固件二进制、依赖与硬件约束、通用 agent 的真实执行行为，而不是“此前没有人研究环境准备”。

第四，“模拟替代”有潜在价值，但必须说清测量对象。公开模拟、放弃真实目标后的概念演示、误判成功和伪造成功证据不同；隐藏的评分标准与模糊的任务要求也可能制造差异。如果 agent 从未看到评分器、也没有获得评分反馈，不宜直接称为 reward hacking；看到模拟行为也不能推出主观欺骗意图。

## 建议主线与研究问题

主线建议：**从 CVE ID 到可验证的真实固件目标，通用 LLM agent 的复现流程在哪些地方中断，它们如何应对这些中断？**

“能力”在正文中应指给定模型、OpenCode、prompt、工具、ARM64 主机和预算构成的 agent 系统表现。单一 harness 的模型切换不能分离所有模型本征能力，也不足以推出“更大模型/更强推理没有帮助”。

建议四个问题：

1. **RQ1：实际达到了什么结果？** 分开描述可核实的目标获取、服务运行、指定漏洞触发、模拟与仅声明成功，报告重复运行的稳定性。
2. **RQ2：流程在哪里受阻？** 以轨迹和产物描述最早未满足的前提、尝试、错误反馈和终止原因。标注未知，允许一条运行有多个障碍。
3. **RQ3：失败后如何改变策略？** 对比重试、替换下载源、依赖修复、调整重托管方式、切换模拟、放弃等可观察行为，比较同 CVE 的成功与失败轨迹。
4. **RQ4：移除某类障碍后会怎样？** 通过提供固件、可运行服务或诊断反馈的受控条件，检验对瓶颈的解释。现有自然轨迹不能独自回答该问题。

六阶段不应被描述为所有案例必然严格遵守的顺序：实践可能在获取、定位、配置和验证间反复迭代。可将阶段作为产物/状态类别，另用事件序列记录回退和跨阶段活动。

## 现有数据可以支撑什么，不能支撑什么

| 可能的叙述 | 现有材料可支持的程度 | 需要补的证据 |
| --- | --- | --- |
| 某些运行停在固件获取/服务启动之前 | 可做描述性结论 | 人工核验事件、产物和原因，解释空目录 |
| agent 经常用模拟方案替代真实目标 | 有待按一致定义核验的观察 | 区分曾模拟/终止于模拟、公开模拟/错误宣称成功 |
| 提供环境会显著提高成功率 | 当前只能作为假设 | 同 CVE、同模型和预算的配对干预 |
| NVRAM/跨 ISA 是主要瓶颈 | 轨迹可能提供线索 | 依赖错误证据；区分 host 架构、仿真模式、厂商差异 |
| 某模型的后期复现能力更强 | 当前排名不能直接证明 | 相同的后期起点，避免不同幸存子集比较 |
| 此研究可估计所有 IoT CVE 的成功率 | 当前不能 | 更合理的抽样框与覆盖；增加重复运行不等于增加案例多样性 |

30 个 CVE、5 个模型、3 次运行，是 450 个运行观察，不是 450 个独立漏洞。按 CVE 配对、聚类计算不确定性；如存在明显厂商/共享固件依赖，还需说明更高层聚类。30 个案例不适合支撑有很多控制变量的复杂模型，优先少量预先说明的比较、效应量和不确定性，避免到处检验后挑显著结果。

只分析成功获取固件的运行可以描述后续过程，但各模型进入该集合的条件不同，不能据此单独证明后期能力高低。同理，轨迹中某工具频繁出现不证明它必不可少；Patch-to-PoC 的 GDB 移除结果正好说明这一点。

## 实验不变时，可以怎样重写

可以保留历史运行，先完成证据审计、重新分析与人工标注，写成**边界明确的探索性实证研究**。这不是把 benchmark 这个词全局替换成 study：

- 引言以安全分析工作流的未知问题开场；将“需要一个新排行榜”换成“需要知道真实固件目标的复现过程和失败行为”。
- 贡献改为实验研究设计、经审计的轨迹发现和开放研究资源；结论未验证前不要预写“证明主要原因”。
- 数据部分描述有目的的分层选例、筛选限制和环境条件，不再称其代表整个 IoT 漏洞生态。
- 方法部分强调证据链、成功定义、行为编码规范、双人标注与分歧处理。LLM 可辅助整理，但关键结果由人工及可执行检查支撑。
- 结果按 RQ 和发现组织；模型表退居一个结果，深入解释同一案例中不同运行如何走向不同结局。
- Plan 与阶段分保留作辅助描述，弱化 20/80 加权 overall 的中心地位。attempt 只记录尝试，不把它混同于完成状态。
- 增加 threats to validity：构念、内部、外部、结论有效性；明确“未观察到”与“没有能力”的区别。

现有 450 次运行不必全部推倒重来，但旧稿中的数值和因果语言不能不经审计直接搬过去。若不补新 agent 实验，我会把论文目标限定为描述性/探索性贡献，对 USENIX 竞争力保持保留判断；是否足够取决于发现是否新颖、证据是否细致，而不是分类名称。

## 最有价值的少量补充工作

以下是研究建议，不是 CFP 硬性条款。优先保证核心发现可靠，无需为了表面规模把所有维度做满。

**不用新增 agent 运行：** 对声称成功的运行核验真实目标；建立事件级证据表，双人标注分层样本并报告一致性；展示同 CVE 成败对照；重新计算条件指标及每次/三次尝试结果；从实际 trace 提取时间、成本和策略切换。不能仅靠让另一个 LLM 概括轨迹完成这一层验证。

**第一组新增运行：环境干预。** 在覆盖不同 ISA/服务复杂度的小型配对子集，比较原始 CVE-only、提供固件、提供真实运行环境。保持目标、模型和预算口径一致。报告准备这些干预环境的人工工作，C 条件建不起来的案例也要记录。提供固件本身会减少版本搜索等不确定性，不应把所有差异都解释为纯下载能力。

**第二组：明确真实目标要求。** 对比原始任务与明确要求真实固件及允许报告失败的任务，检查模拟替代及错误成功声明是否改变。若只减少模拟但不提高真实成功，这仍然是有价值的负结果；不能声称提示词修复了复现能力。

**第三组按发现选择：诊断干预或外部检验。** 如果依赖修复是最突出机制，提供特定诊断信息并与无信息条件配对；如果担心结论仅是 OpenCode 特性，则在第二 harness 上复测核心发现。后一项检验的是行为模式能否复现，不必重做完整排行榜。

干预子集最好在查看干预结果前明确选择规则、主要比较与成功定义；保留负结果。不要只从已经能手工启动的简单案例中选择，然后外推到全体。

## 题目、命名与摘要的讨论稿

建议暂时保留 ReproBench 作为数据、代码及研究平台的名称，正文题目突出科学问题。它已以预印本名称被其他研究引用，改稿应保持版本和资源对应关系；没有必要仅为摆脱 benchmark 期待抹掉已有名称。

可选题目（是定位草案，不代表研究已证明题中结论）：

1. **From CVE IDs to Real Firmware: An Empirical Study of LLM Agents for IoT Vulnerability Reproduction**
2. **Where LLM Agents Stall: An Empirical Study of IoT Vulnerability Reproduction from CVE IDs**
3. **ReproBench: An Empirical Study of LLM Agents Reproducing IoT Vulnerabilities from Scratch**

我优先选 1，任务和对象最明确，且不提前宣称发现了哪种机制。2 需要正文有深入的失败过程分析；3 便于保留名称但读者仍可能预期有可复用 benchmark。

摘要可按此结构重写：

> 现实中，从公开漏洞标识得到可验证的复现结果，需要获取并重建目标环境。我们研究通用 LLM agent 如何完成 IoT 固件漏洞的这一流程。在明确的选例和运行条件下，分析 30 个 CVE、5 个模型、3 次重复运行的执行轨迹与产物。使用真实目标执行证据和人工核验区分复现、部分进展、模拟与无法判定结果。随后按经验证的结果报告主要发现、适用范围及对安全分析工作流的含义。公开 ReproBench 的案例、协议与可共享证据以支持复查。

这里故意没有填入 45.3%、5.3% 或“最大瓶颈”，因为定义、证据完整性及统计口径尚待确认；也没有将单一 harness 结果表述为模型的普遍能力边界。

## 我建议接下来讨论的选择

主线采用“环境重建中的真实工作流障碍”，模拟替代作为其中一个重要行为结果；将“可信成功证据”作为贯穿研究的测量方法。这最贴近 IoT 特点，也最能利用已有数据。

如果重新标注显示模拟行为的类型、发生时间和触发条件比架构/依赖机制更有区分力，可以把主线转为“从真实复现退向模拟的行为及评估后果”。这需要与普通概念验证、提示词歧义、预算耗尽和诚实失败明确区分，否则新颖性容易被既有工具使用失败研究覆盖。

最终选择应由重新核验的轨迹决定。现在可以先确定研究问题与写作结构，保留原始实验，再用少量针对性的对照检验最有价值的解释。
