# USENIX Security 2027 论文大纲 v1：实证研究路线

状态：供作者审阅的结构草案。日期：2026-11-19。

已采纳的方向：保留现有实验作为研究基础；取消 Plan/Task/Overall 加权打分，以可验证结果、六阶段过程、执行障碍和应对行为组织论文。本文档不预设新的实验结果，不把待核实的历史统计写成确定结论。

## 一、论文定位与中心问题

**建议题目**

From CVE IDs to Real Firmware: An Empirical Study of LLM Agents for IoT Vulnerability Reproduction

中文工作标题：从 CVE 标识到真实固件：LLM 智能体复现 IoT 漏洞的实证研究。

ReproBench 保留为案例集、协议及研究资源名称；标题是否保留该名称可在成稿时决定。

**中心问题**

通用 LLM 智能体从 CVE ID 开始复现已知 IoT 漏洞时，实际完成了什么，在哪些环节受阻，以及受阻之后如何继续行动？

**三个研究问题**

- RQ1 — Outcomes：在给定实验条件下，智能体获得了哪些可验证的复现结果？
- RQ2 — Barriers：在真实目标的获取、分析、重建与触发过程中，出现了哪些可观察的障碍？
- RQ3 — Responses：面对这些障碍，智能体如何重试、修复、切换方法、转向模拟或终止？

RQ2 描述工作流与系统约束，RQ3 描述应对行为。二者都保留。观察到障碍与模拟先后发生，不自动证明前者导致后者。

**建议的三项贡献**

1. 一项边界清楚、以轨迹和产物为依据的 IoT 已知漏洞复现实证研究；历史实验包含 30 个 CVE、5 个模型、每组 3 次运行，最终分析范围由证据完整性审计决定。
2. 对可验证结果、执行障碍与应对行为的系统分析，呈现经核验的发现及其适用范围；具体 findings 在分析后填写。
3. 支撑复查的开放研究资源，包括案例元数据、执行协议、证据判定规范、可共享轨迹与分析工具，统称 ReproBench。

贡献 2 不能提前写为“证明环境是主要瓶颈”或“揭示模型普遍欺骗行为”。

## 三、逐节大纲

### Abstract

建议按五步展开：

1. 已知 IoT 漏洞的动态复现需要获取和运行正确固件目标；自动化完成这一流程的实际表现仍需要细致研究。
2. 说明研究对象、案例选择范围、模型、harness 及重复运行；CVE ID 是唯一实例特定初始输入，仍包含统一任务提示和工具环境。
3. 说明依据真实执行证据和轨迹分析结果、障碍与应对行为，不采用加权能力分数。
4. 报告 2–3 条分析后成立的主要发现，数字均来自统一证据口径。
5. 给出对自动化安全分析的具体含义及资源可用性。

不直接搬入旧摘要的 45.3%、5.3%；先重新核实定义、分母和证据。

### 1. Introduction

**1.1 实际问题：一个 CVE 并不是一个就绪的执行目标**

从安全分析人员需要确认漏洞影响、验证公开报告或准备动态分析环境的场景切入。将获取匹配固件、定位目标组件、满足运行依赖、启动服务和验证触发连接起来。

可以用一个经核验的简短案例开场：已知漏洞信息清楚，但服务启动遇阻；随后同一案例的不同运行采取不同方法。此处只引出问题，不先宣布频率或主要原因。

**1.2 研究缺口：实际执行过程与行为仍需解释**

简述既有研究有不同起点：现成环境、源码/补丁、自动重建流程。准确承认 CVE-GENIE、K-Repro 等工作，说明本研究聚焦通用 coding agent 面对 IoT 固件约束的行为和证据。

**1.3 研究问题与研究概览**

给出 RQ1–RQ3，简述 30×5×3 的历史设计、真实目标证据和过程分析。将模型比较放在研究设计之中。

**1.4 主要发现与贡献**

最终填入经核验的发现。现阶段只保留占位：结果分布、障碍特征、应对行为；不预先为结果取带结论的标题。

### 2. Task Definition and Research Context

**2.1 研究的是已知漏洞复现**

定义输入、可用资源、输出及任务范围。区分已知漏洞复现、未知漏洞发现、完整利用链构造和漏洞修补。

解释“从 CVE ID 开始”与“作者选择有公开资料、可获取固件的样本”是两个不同层面的限制；不声称样本代表任意 IoT CVE。

**2.2 真实固件目标与模拟方案**

- 真实目标：来源可核实的受影响固件二进制或相关原始组件，确实在被分析的执行环境中运行并接收测试输入。
- 合法的研究性重托管可使用 QEMU、chroot、依赖桩等；是否有效取决于它们是否保留所研究的漏洞语义，不能一律将桩或仿真等同于模拟漏洞逻辑。
- 模拟方案：重新实现目标服务或漏洞逻辑，而未在所声称的真实漏洞目标上完成验证。
- 不要求全部案例都启动完整固件或在物理设备上运行，范围必须明确。

**2.3 六类工作活动与相关研究**

沿用信息收集、固件获取、固件提取、二进制定位/分析、服务重托管、漏洞触发六类活动；它们是分析框架，允许迭代、回退和跨阶段行动。

相关研究按初始资源、环境准备责任、目标类型与验证方式比较。重点包括 CVE-Bench、CyberGym、BountyBench、SEC-bench、CVE-GENIE、K-Repro、FirmAgent 及能力实证研究。避免长篇通用 LLM 或漏洞检测历史。

### 3. Study Design

**3.1 Case Selection and Reference Validation**

说明 696 个候选到 30 个案例的过程、筛选理由和均衡三类漏洞的研究目的。报告年份、厂商、设备类别、ISA、固件规模和依赖复杂度等可可靠获得的信息；缺失项标为未知。

区分公开参考资料、人工核验的事实与实际完成的参考复现。记录版本冲突、失效链接和参考更正，不能把文献中存在 PoC 当作本研究已经重放成功。

**3.2 Agent Execution Protocol**

描述五个模型、OpenCode、主机架构、工具、容器隔离、网络和权限、统一提示、预算、停止条件及三次重复运行。尽可能还原实际模型 ID、版本和运行日期。

旧实验曾要求 agent 写计划和报告，这个执行协议应如实保留；删除 Plan Score 不代表过去没有计划步骤，也不将旧实验描述为经过新提示词运行。

**3.3 Evidence Collection and Completeness**

解释如何关联 CVE/model/run、workspace、trace、模型报告及评分之外的原始产物。

报告历史 450 个运行位置的完整性；已发现部分 trace/workspace 目录为空，需区分采集遗漏、迁移问题、执行失败与原因不明。记录不同分析的可用分母，避免静默丢弃。

**3.4 Outcome and Progress Assessment**

建立证据判定规范，不设置分值。每条运行至少分别记录：

| 维度 | 记录内容 | 关键约束 |
| --- | --- | --- |
| 漏洞触发结果 | 已验证触发／在观察充分的运行中未完成触发／证据不足无法判定 | 未完成不代表普遍不具备能力；成功须对应同一条运行 |
| 过程状态 | 各类产物是否获得、版本是否匹配、真实服务是否运行 | 各状态有证据、反证或未知，不用任意分数衡量质量 |
| 目标执行方式 | 真实目标／模拟／二者均出现／二者均未确认／未知 | 模拟与真实执行不是互斥的终局标签 |
| agent 的自述 | 声称成功／部分进展／失败／表述不清 | 自述不作为事实证据，可与验证结果交叉比较 |

真实触发依据包括目标来源与身份、执行日志、输入到达目标以及漏洞特异性信号；必要时检查无害输入或修补版本。分别制定崩溃、命令注入和认证/访问控制问题的证据要求。

六阶段状态和最终成功分开。不得用多个重复运行各自的最好阶段拼出一次不存在的完整复现。

**3.5 Barrier and Response Coding**

说明从轨迹中定位“行动—反馈—下一步”的事件序列，为障碍和响应分别编码。类别可先基于旧稿建立初始表，再通过试标注修订并冻结；新增类别和不确定样本保留记录。

LLM 可辅助检索和整理证据，关键标签需人工核验。对抽样单位、分层规则、独立标注者、标注一致性和分歧裁决如实报告；不能将尚未完成的双人标注写成既成事实。

**3.6 Analysis Strategy**

区分运行级和 CVE–模型组级结果、首次和多次尝试。给出比例、分母和不确定性，按 CVE 配对/聚类；避免将 450 次运行视为 450 个独立漏洞。

阶段条件比例用于描述进入该阶段的运行，不据此推断模型后期能力的因果高低。基础设施错误、预算耗尽和安全拒绝分别记录，不都归为技术能力不足。

### 4. Reproduction Outcomes — RQ1

**本章问题：智能体最终取得了什么可核实的结果？**

**4.1 Verified Outcomes Across Cases and Models**

报告真实触发、未完成和无法判定的结果；并列呈现各模型表现及不确定性。解释分母与证据覆盖，区分每次成功与三次尝试至少一次成功。

**4.2 Progress Toward a Real Target**

展示正确固件、提取产物、目标二进制、真实服务和漏洞信号等状态分布。图示应允许不适用、未知和实际路径差异，不强行呈现严格串行漏斗。

**4.3 Variation Across Repeated Runs**

报告同 CVE、同模型的三次运行是否一致，区分一次偶然成功和可重复完成。展示案例差异，避免把最佳一次当作典型表现。

**本章收束：** 回答观察到的复现范围与稳定性；障碍原因交给下一章。

### 5. Barriers to Reproduction — RQ2

**本章问题：哪些实际条件阻碍了真实目标的复现？**

**5.1 Acquiring and Identifying the Correct Target**

分析下载不可达、型号/版本混淆、压缩包或更新包不匹配、固件内容不完整等。区分暂时网络失败与可持续的获取障碍。

**5.2 Reconstructing an Executable Service**

分析 ISA/ABI、动态加载器与库、NVRAM、文件系统布局、初始化、设备节点及网络配置等。按证据归纳，某类没有足够案例时合并或移入附录。

**5.3 From a Running Service to the Specified Vulnerability**

区分服务在运行、接口可达、输入进入目标函数和出现漏洞特异信号。分析认证状态、配置、协议和参数前提等障碍。

**5.4 Cross-Case Patterns and Paired Examples**

展示障碍分布与同案例对照：某次在获取阶段停下，另一次获取成功但启动失败，第三次可能走得更远。明确“最早未满足的条件”“多个观察到的障碍”“终止原因”不同。

厂商、ISA、主机架构和仿真模式可能混淆，不能直接把观察差异写成某一种架构的必然能力上限。

**本章收束：** 总结有证据支持的系统约束及待检验解释；不宣称消除它们必然带来成功。

### 6. Responses to Barriers — RQ3

**本章问题：受阻之后，智能体做了什么，以及这些行为与后续结果如何关联？**

**6.1 Continuing on the Real Target**

分析更换获取源、修复依赖、调整执行方式、修改配置、使用反馈定位错误等行为。区分有新信息的修复和没有实质变化的重复。

**6.2 Transitioning to Simulation**

记录首次模拟的时间、之前的反馈、是否曾尝试真实目标、模拟内容及后续是否回到真实目标。报告“曾使用模拟”与“最终以模拟结束”两种不同口径，不混用。

**6.3 Reporting Outcomes and Stopping**

将 agent 报告与证据比较，区分明确说明模拟、说明未完成，以及证据不支持的成功声明。独立记录超时、预算、拒绝和主动停止。

不把模拟一概视为伪造，不从结果推断动机，也不在没有评分反馈的实验中直接使用 reward hacking 作为行为解释。

**6.4 Contrasting Trajectories on the Same CVE**

建议选取 2–3 个经核验的对照：真实修复与模拟替代；发现问题后修正与重复失败；真实成功与不受证据支持的自述。选择规则应透明，给出跨样本计数支持，不以个别故事代替全局分析。

**本章收束：** 说明环境障碍与应对行为如何在观察中连接；仅在有进一步对照时讨论因果解释。

### 7. Discussion and Threats to Validity

**7.1 Implications for Automated Security Analysis**

围绕已得到的发现，讨论哪些环节适合自动化、何时需要专门重托管工具或人工介入、什么证据足以支持复现声明。建议必须与结果相连，避免泛泛要求“更强模型”“更好工具”。

**7.2 What the Study Does and Does Not Establish**

明确结果属于给定样本、模型、harness、提示、预算和主机条件；不是未知漏洞发现能力，也不是所有 IoT CVE 的总体成功率。讨论参考资料与模型训练污染的可能影响。

**7.3 Threats to Validity**

- 构念有效性：真实目标和漏洞特异性信号是否判断正确；重托管桩是否改变了漏洞语义；行为标签是否准确。
- 内部有效性：工具配置、服务状态、网络可达性、模型路由及采集缺失等是否影响观察。
- 外部有效性：30 个经筛选案例、三类漏洞、单 harness 和 ARM64 主机的限制。
- 结论有效性：样本聚类、三次重复的分辨率、小分组、未测混淆与选择性案例分析。

### 8. Conclusion

用一段回答三个研究问题，总结经证据支持的发现和实践意义。ReproBench 的开放资源作为复查入口。避免在结尾新增结果或提出未经检验的普遍能力断言。

## 五、附录与开放材料

- Open Science：说明代码、案例元数据、执行协议、轨迹与产物、分析工具的访问方式，以及固件再分发和不能公开材料的限制。
- Ethical Considerations：已知漏洞、隔离运行、访问范围、第三方服务及数据处理；只描述实际执行的措施。
- 完整案例与参考核验表：版本、来源、哈希、目标组件、已核实事实、未解决冲突。
- 完整提示词、运行配置、模型信息和停止条件。
- 证据判定规范、行为 codebook、一致性与分歧处理细节。
- 补充案例、逐次状态与稳健性分析。

不需要为已取消的评分体系保留一章算法论证。历史评分 JSON 可保留作溯源，但不作为新稿最终结论的未经核验来源。

## 七、现有实验与补充实验的边界

**本大纲的基础版本不要求新增 agent 运行。**需要完成的是对历史资料的核验、重新标注与统计分析；数据足够且发现明确时，可写成边界清楚的探索性实证研究。

以下是增强解释的可选补充，不预先写进贡献，也不在结果里留假定提升的空表：

1. 同案例的 CVE-only／提供固件／提供就绪真实环境对照：检验移除环境障碍的效果，可并入 §5。
2. 原任务提示／明确真实目标要求且允许失败报告对照：检验模拟与成功声明的变化，可并入 §6。
3. 第二 harness 或针对性诊断反馈：根据最终最重要的发现选择，检验该发现的范围或解释。

若开展某组补充实验，应在 §3 补充设计，并在对应结果章呈现包含负结果的完整比较。仅描述自然运行的章节不使用因果性结论。
