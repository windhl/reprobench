日期：2026-11-19。状态：供作者审阅，替代 v1 作为当前推荐结构；v1 保留作讨论记录。本次更新论文组织和论证任务，未修改 LaTeX 正文、历史实验或评分代码。

依据：已保存论文的方法、结果与讨论部分，尤其是人工漏洞复现、Web PoC、企业网络 agent 及阶段解耦研究。比较和写作原则见[实证研究写法总结](../../../references/empirical-related-work-2026-11-19/notes/empirical-study-writing-guide.md)。

## 一、重新明确文章要交付的认识

**建议工作标题**

Understanding LLM Agents in IoT Vulnerability Reproduction: An Empirical Study

中文：理解 LLM 智能体的 IoT 漏洞复现表现与行为：一项实证研究。

这个题目突出研究对象；“从 CVE ID 开始”在摘要和研究设计中准确交代。v1 的 *From CVE IDs to Real Firmware* 仍可作为备选，但需要避免让标题暗示所有运行都已经抵达真实固件执行。ReproBench 可保留为研究资源名称，是否放在标题中不影响文章的论证结构。

**中心问题**

在所研究的 CVE、agent 配置和运行条件下，LLM 智能体从 CVE 标识开始，能在真实 IoT 漏洞目标上完成什么；复现过程在哪里受阻；遇阻后怎样行动、取得哪些后续进展，其最终报告与执行证据是否一致？

最后一个问题先以过程观察和描述性比较研究，不据此默认获得干预意义上的因果解释。

**建议的研究路线：探索性、以证据为基础的描述与诊断。** 历史运行提供研究材料，重新核验的结果与轨迹分析提供科学认识。若后续观察引出值得检验的解释，再选择补充实验；新系统、新打分方法或全面干预实验不预先列为贡献。

## 二、三个研究问题及其逻辑连接

| 研究问题 | 建议英文表述 | 需要回答的内容 | 如何引出下一个问题 |
| --- | --- | --- | --- |
| RQ1：实际复现表现 | To what extent do LLM agents reproduce known IoT vulnerabilities under the studied conditions? | 真实触发、部分进展、证据不足，以及同配置重复运行的变化 | 结果分布说明完成程度，还需要看未完成的运行遇到了什么 |
| RQ2：执行受阻的位置与条件 | Where does reproduction break down, and what observable conditions are associated with these breakdowns? | 未满足的前提、可观察的执行障碍、过程位置和跨案例差异 | 同类障碍下行为可能不同，需要继续分析下一步行动 |
| RQ3：遇阻后的行为与结果表述 | How do agents respond to reproduction obstacles, and how do their subsequent actions and reports relate to observed progress? | 修复、重试、替换路径、模拟、停止，以及报告与证据的对应 | 将结果、条件和行为连起来，为 Discussion 提供基础 |

模型配置是三个问题共同的比较维度。六类工作活动是定位执行过程的坐标。环境重建是 RQ2 的重要候选分析内容；从真实目标转向模拟是 RQ3 的重要候选分析内容。二者都保留，重要程度和最终 findings 根据核验结果决定。

注意：这是在已有实验和初步观察之后制定的分析框架，应如实说明分析的探索性；不能将其叙述为运行前已注册的三个假设。

**贡献的建议写法**

1. 对从 CVE 标识开始的 IoT 漏洞复现开展实证研究，明确研究条件、样本选择和证据判定；历史设计为 30 个 CVE、5 种模型配置、每组 3 次运行，实际分析数量由数据审计确定。
2. 结合可验证产物和执行轨迹，分析复现结果、执行障碍与应对行为，并报告经核验的发现及其边界。
3. 开放支撑复查的案例元数据、实际运行协议、证据规范、可分享轨迹与分析工具，统称 ReproBench。

最终成稿时，第 2 项应替换为具体发现及其认识价值，不能长期停留在“做了三类分析”的活动清单。

篇幅为正文写作预算，约 12.5 页，非固定排版要求；参考文献与附录另行安排。

## 四、逐节名称、内容与行文顺序

### Abstract

建议用一个段落依次写：实践问题与未知之处 → 所研究的条件和材料 → 结果与轨迹分析方法 → 2–3 条核验后的发现 → 具体含义与资源。

应包含可验证的结果，避免摘要最终只写“我们分析了多个模型和多类障碍”。旧稿的模拟比例或分数推导成功率，须先按新定义核查才能引用。

### 1. Introduction

**段落 1：实际场景。** 从确认已知 IoT 漏洞的需求切入，说明拿到 CVE 标识之后仍须找到匹配目标、准备可运行环境并验证触发。可以使用一个短例，但应基于真实、经核验的执行记录。

**段落 2：为什么已有结果没有充分回答这个问题。** 已有研究覆盖就绪环境中的攻击、基于源码/补丁的 PoC 生成和自动重建。承认其能力与范围，进一步指出我们研究的特定组合：IoT 固件、通用 agent、以 CVE 为实例输入、实际执行过程与目标证据。

**段落 3：仍缺少的认识。** 在这些条件下，完成了什么、失败发生在哪里，以及遇阻后怎样继续，尚需在同一批执行记录中连接分析。这里建立知识缺口，不以“漏洞数量比其他工作少”或“我们第一个”作为出发点。

**段落 4：研究问题和设计概览。** 给出 RQ1–RQ3，说明重复运行、产物核验与轨迹分析。CVE ID 是实例特定起点，实验仍包含统一任务提示和工具环境。

**段落 5：主要发现。** 每条用“经核验的规律 + 支持范围/关键数字 + 对问题的含义”表达。现阶段保留占位，不先写“环境是最大瓶颈”或“模型通过模拟作弊”。

**段落 6：贡献。** 以知识贡献为中心，研究资源支撑复查。避免按数据集、评分器、榜单的顺序组织贡献。

### 2. Background and Task Definition

#### 2.1 IoT Vulnerability Reproduction

定义已知漏洞复现任务、输入、目标及期望产物，区别于发现未知漏洞和漏洞修复。解释固件打包、异构指令集、运行依赖和设备状态为什么与任务相关；只保留理解后文需要的知识。

简述六类工作活动：信息收集、固件获取、提取、目标二进制定位/分析、服务重托管和触发。称为活动而非必须顺序通过的六道关卡，允许回退和循环。

#### 2.2 Target Execution and Reproduction Evidence

解释真实目标、服务重托管、模拟漏洞逻辑、目标运行和漏洞触发等概念。QEMU/chroot/必要桩并不自动使复现无效，关键是目标来源与相关漏洞语义。

本节提供概念；具体需要哪些证据、谁来判定、如何处理不确定性在 §3.4。正文不应要求每个案例都完整启动固件或使用物理设备，除非这确实是任务定义。

### 3. Study Design

#### 3.1 Research Questions and Analysis Overview

回顾三个问题及设计依据，给出研究流程图。说明实验执行与后续探索性分析的时间关系。用小表对应 RQ、所需证据和分析方式，帮助读者预期 §4 怎样回答问题。

#### 3.2 Case Selection and Reference Validation

从候选到最终案例的选择过程、纳入和排除标准、三类漏洞的选择理由，以及可核实的厂商、年份、ISA、固件和依赖信息。30 个样本的意义在于研究明确情形，覆盖与偏差都需说明。

区分公开描述/参考 PoC、作者已核验的目标事实和作者真正完成的参考复现。参考信息若存在版本冲突或未重放，应明确记录。

#### 3.3 Agent Configurations and Execution Protocol

报告实际模型 ID、运行时间、OpenCode/harness、提示词、主机架构、工具、网络权限、预算、停止规则与三次重复。

旧实验要求的计划和报告属于历史协议，如实保留。取消 Plan Score 不改变历史执行条件。比较的对象是这些模型在该配置下的 agent 系统，不是脱离工具和预算的内在能力。

#### 3.4 Evidence Collection and Outcome Assessment

将 CVE/model/run 与 trace、workspace、报告和产物关联，报告证据完整性和不同分析的可用数量。空目录需要审查来源，不能自动计为失败或直接删去。

采用以下相互独立的记录维度，不计算总分：

| 维度 | 示例标签/内容 | 用途 |
| --- | --- | --- |
| 实际复现结果 | 经验证触发／可观察记录中未完成触发／证据不足无法判断 | RQ1 的主要结果 |
| 过程进展 | 正确固件、提取产物、目标组件、服务运行、漏洞特异性信号，各自记录证据与未知 | RQ1 与 RQ2 |
| 目标与执行方式 | 是否执行原始目标、是否重新实现漏洞逻辑、是否在两者之间切换 | RQ2 与 RQ3 |
| agent 自述 | 声称成功、部分完成、失败或不清楚；是否明确说明模拟 | RQ3 中与证据交叉比较 |

成功必须有同一条运行的目标身份、执行与特异性漏洞信号支持。按漏洞类型给出判定规则，必要时检查无害输入或修补版本；说明哪些已经做、哪些仍不确定。不能从三次运行分别取得的阶段产物拼出一次完整成功。

#### 3.5 Trace Coding and Analysis Strategy

将轨迹中的“行动—反馈—后续行动”作为过程证据，分别编码障碍和响应；明确事件级、运行级和 CVE 级分析的区别。

先用部分轨迹试标注、修订 codebook，再分析其余材料；若执行双人标注、抽样核验或一致性分析，报告实际人数、比例和裁决方式。LLM 可协助检索，不以未经核验的 agent 判分代替关键事实。

报告分母、缺失、多标签计数、描述性比较和不确定性。重复运行按 CVE/配置成组分析；若估计区间或配对差异，应说明对应单位和方法，不能把 450 次当作 450 个独立漏洞。三次重复支持有限的运行间比较，不足以精准估计单个 CVE 的成功概率。

进入某阶段的条件成功率可描述实际执行路径；各模型抵达该阶段的案例可能不同，应避免据此比较纯粹的后期能力。基础设施故障、预算终止和安全拒绝分别处理。

### 4. Empirical Results

三个 RQ 共享 §3 的方法。在各小节中只交代局部口径和必要细节，以“观察—证据—解释—回答”推进。模型分组、案例分组和重复性为分析维度，不必各自重复整套实验介绍。

#### 4.1 RQ1: Reproduction Outcomes and Progress

**读者需要知道：实际完成了什么，这些结果有多稳定？建议约 1.3 页。**

1. 报告可核验运行数量与证据覆盖，再展示真实触发、未完成和无法判断的结果。保留无法判断，说明其对比例解释的影响。
2. 按模型配置和案例呈现差异，清楚区分逐次成功和三次至少一次成功，先描述后解释。
3. 用状态矩阵或分组分布展示终点之外的真实进展，避免总分和严格线性漏斗。
4. 分析同 CVE、同配置重复运行是否一致；将成功证据或一个简短对照放在结果附近。
5. 用短段落回答 RQ1，再提出下一步问题：这些未完成的执行具体停在什么地方？

**主要图表：** 结果分布及未知比例；过程状态与运行间变化可合并为一幅图或紧凑表。

#### 4.2 RQ2: Where Reproduction Breaks Down

**读者需要知道：哪些前提没有满足，观察到的障碍如何分布？建议约 1.8 页。**

1. 说明障碍分析的覆盖范围、事件定义和分母，区别“出现过的障碍”“最早未满足条件”和“终止时障碍”。
2. 按实际证据分析目标准备、可执行环境和漏洞触发三个环节：例如版本识别与下载；加载器/库/配置/设备状态；服务可达之后的协议与漏洞前提。具体分类由标注结果决定。
3. 报告分布并提供有代表性的短轨迹。只统计进入相应活动且可观察的运行时，明确这是条件分布。
4. 分析跨案例或同案例的差异，包含能克服相似障碍的反例。区分目标客观不可得、工具或主机限制、agent 未能正确处理已可获得的信息；证据不足则标未知。
5. 回答哪些障碍在研究范围内反复出现，以及哪些解释尚不能确定。

**主要图表：** 障碍类型与工作活动的分布，附可用分母。正文配一到两个过程证据片段，不把所有日志放进正文。

避免把“环境阶段遇阻多”直接写成“提供环境后一定成功”或“所有模型的核心弱点都是环境”。未继续运行的后期能力在这些记录里没有被观察到。

#### 4.3 RQ3: Agent Responses and Outcome Reporting

**读者需要知道：遇阻后如何行动，这些行动和最终自述对应什么事实？建议约 2.1 页。**

1. 分析实际响应：利用反馈修复、寻找新资料、更换真实执行方式、重复原策略、重新实现目标/漏洞逻辑、停止。允许同一次运行出现多个行为。
2. 重点检查模拟的发生时序和含义：首次出现于何时、之前实际发生什么、是否返回真实目标。分别统计“曾进入模拟”和“终局以模拟为主”，不混用旧稿两种比例。
3. 研究后续进展与报告：继续修复是否获得新证据；模拟是否明确声明；成功声明是否得到同次运行的真实目标证据支持。公开说明的模拟、诚实报告失败和证据不足的成功声明分别呈现。
4. 选取同 CVE 的对照轨迹，将“遇到的反馈—下一步行动—之后产物—最终表述”放在一条时间线上。说明案例选择规则，并用全局统计限定它的代表性。
5. 回答观察到哪些应对模式，以及它们与实际进展、目标选择和报告之间的关系。

**主要图表：** 响应分布/转换图；两条对照轨迹；自述与证据交叉表可根据内容压缩或放附录。

该节不预设模拟是最主要现象，也不推断动机或使用未经检验的 reward hacking 解释。重新实现漏洞逻辑与保留漏洞语义的真实组件重托管须区别处理。

**三个小节统一的收束方式**

每个 RQ 最后用短段落或简框给出答案。最终标题可以体现经验证的发现；在数据分析完成前使用上述中性标题。发现必须具体到结果、模式或差异，避免“模型仍然面临挑战”这类通用结论。

### 5. Discussion

#### 5.1 Interpreting Reproduction Performance

综合 RQ1–RQ3：终点结果、执行条件和遇阻后的行为如何共同影响我们对“复现能力”的认识？哪些观察与原先预期不一致？替代解释是否仍存在？

这里应从结果中提炼有价值的理解。例如，若证据支持，可讨论“生成了能运行的演示”和“在指定真实目标上复现”的差距，以及未就绪环境如何限制对后期能力的判断。它们目前是讨论方向，尚非已成立的核心 insight。

#### 5.2 Implications for Agents and Their Evaluation

从具体发现推导建议，例如哪类前提值得外部工具支持、何时应请求人工协助、为何需要报告目标来源与执行证据。每条建议回指相应结果。

区分研究支持的评价建议与尚待验证的性能改进。若没有改提示实验，就不能写“允许失败报告已解决模拟替代”。

不在此重复三张模型结果表，也不加入一章尚未实施的新系统方案。

### 6. Threats to Validity

将每类威胁、已做措施和剩余影响对应写清楚：

- **Construct validity：** 真实目标与漏洞信号是否判断正确；桩是否改变语义；报告和行为分类是否可靠；证据缺失能否影响结论。
- **Internal validity：** 主机架构、harness、提示、预算、工具状态、网络和模型服务错误可能共同影响表现；自然发生的响应选择存在混淆。
- **External validity：** 经筛选的 30 个 CVE、三类漏洞及固定 agent 配置对其他漏洞、设备、模型版本和工具环境的推广限制。
- **Conclusion validity：** CVE 聚类、每组仅三次重复、较小子组、多次探索和案例选择限制差异解释。

模型可能记忆公开案例也应讨论；不能声称所有生成均来自未见过漏洞上的独立推理。探索性分析本身应透明呈现。

### 7. Related Work

按研究问题组织，建议三段/小节。前面的 Introduction 仍需点明最直接的先行工作。

#### 7.1 Vulnerability Reproducibility and PoC Generation

Mu 等人工复现研究；Web PoC；Patch-to-PoC/K-Repro；CVE-GENIE。沿输入资料、目标准备责任、目标类型和结果核验比较。准确承认已有环境构建研究。

#### 7.2 Empirical Studies of Security Agents

企业网络、CTF、本地提权、功能属性、重复性与阶段解耦研究。比较全局表现、轨迹分析、失败分类及受控干预分别能回答什么；说明本研究补充 IoT 固件复现这一任务条件中的过程证据。

#### 7.3 Evaluation Resources for Security Agents

与 CVE-Bench、CyberGym、BountyBench、SEC-bench 等比较任务起点和执行环境。ReproBench 作为资源支持本研究复查，不需要以最大案例数量或新综合分数作为主要价值主张。

三段可按篇幅合并。不同研究成功定义不同，不将外部成功率直接纳入同一排行榜。正式发表、workshop 和预印本的身份按来源记录准确引用。

### 8. Conclusion

用短段落回答中心问题：在研究边界内发现了哪些实际能力和执行模式，它们为什么影响对自主复现的理解。指向开放材料；不在结尾增加新结论或泛化为所有 LLM 的能力上限。

## 五、相对 v1 的实质调整

| v1 | v2 | 调整理由 |
| --- | --- | --- |
| 三个独立结果章：Outcomes / Barriers / Responses | §4 一个 Empirical Results 章，下设三个递进 RQ | 共享设计和材料，强化前后问题的连接，减少重复介绍；不是格式上的强制要求 |
| RQ2 偏向列出障碍类型 | 增加未满足前提、过程位置、可观察范围和同类障碍反例 | 防止把故障目录直接当成解释或因果排序 |
| RQ3 以应对策略为主 | 将响应、后续进展、目标选择与最终报告连接分析 | 让模拟进入完整过程，而不成为脱离结果的个别故事 |
| Task Definition and Research Context 混含文献比较 | 精简成 Background and Task Definition；完整比较移至 §7 | 区分理解任务需要的概念与确定研究增量的文献讨论 |
| Discussion and Threats 合并 | 独立 §5 Discussion 与 §6 Threats | 分别承担跨发现解释和结论可靠性分析 |
| 大纲主要按分析对象排列 | 明确每节问题、数据、论证顺序和收束答案 | 指导实际行文，减少“换了标题仍在介绍 benchmark”的问题 |
| 对观察与未来对照的边界已有说明 | 更明确为历史数据上的探索性分析，干预结论按实际实验增加 | 对齐真实研究时间线与证据强度 |

保留的核心选择：移除 Plan/Task/Overall 和任意加权评分；保留真实执行证据、六类活动、模型配置比较、环境问题和模拟行为；不预先增加新实验。

## 六、图表、附录和补充实验的安排

**正文图表优先级**

1. §3 研究设计与分析流程；案例和运行配置简表。
2. §3 关键证据判定规则，可用紧凑表，完整 codebook 进附录。
3. §4.1 结果分布、证据覆盖与过程状态；按篇幅合并。
4. §4.2 障碍分布及分母。
5. §4.3 响应模式及同案例对照时间线。

表图各自服务明确问题，不以“必须有多幅复杂图”为目标。完整逐运行结果和案例元数据放开放材料，正文仍需给出关键统计与判定依据。

**附录与开放材料**

- Open Science：可访问的研究资源、复查说明和受限材料说明。
- Ethical Considerations：实际执行的隔离、访问边界、数据处理和共享措施。
- 案例选择与参考验证全表；实际提示、配置和运行时间信息。
- 证据判定、障碍与响应 codebook、人工核验/分歧处理细节。
- 补充轨迹、逐次结果、缺失分布与实际完成的稳健性分析。

**若后续增加实验**

优先围绕分析后最值得鉴别的一种解释选择实验，例如同案例提供就绪真实环境，或改变任务对模拟和失败报告的说明。对应设计加入 §3，结果加入相应 RQ；若形成独立问题再增加 RQ4。报告负结果，不预设必有提升。

现阶段不设置必写的“Proposed Approach”“Intervention Evaluation”或新 agent 架构章。基础版本是否有足够贡献，取决于核验后发现的具体性、深度和认识价值；仅调整章节无法保证这一点。

## 七、从大纲走向正文的建议顺序

1. 先完成证据完整性审计和关键标签试标注，确认三个 RQ 是否都有足够材料。
2. 为每个 RQ 写一页内部结果备忘：最重要观察、支持数字/轨迹、反例、替代解释和可说的结论。发现不突出时先调整分析问题。
3. 写 §3 与 §4，形成证据主体，再根据实际发现写 §5。
4. 最后重写 Introduction、Abstract 和贡献，让全文围绕真正得到的认识展开。

旧稿可迁移的是经核验的任务与数据、执行协议、真实产物和轨迹；原加权表、分数排名和基于分数阈值的成功定义不进入新稿主体。历史原文件保留作溯源。
