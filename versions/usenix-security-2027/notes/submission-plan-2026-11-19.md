两份汇总实现分别为外层 `scripts/generate_evaluation_summary.py` 与仓库 `skills/reprobench-scoring/scripts/generate_evaluation_summary.py`。本次动态加载两份脚本，对上述 JSON 只读调用 `collect_results`，未调用模型重新评分，未覆盖任何结果：

- 模型名称去除显示用的 `-free` 后，匹配到相同的 450 个运行键。
- 4 个运行的 overall 不同，均差 0.4 分：CVE-2021-44158/gpt-5.5/2、CVE-2024-5293/gpt-5.5/2、CVE-2020-13389/claude-sonnet-4-6/2 和 /3。
- 外层脚本对 attempt 分直接加分；仓库版要求无 artifact 分、非基础设施失败且 attempt 已触发。这是应核实的计分差异，不应仅因总分差异小而忽略。
- 历史统计检查记录 136 项检查、13 项差异；其中有过期硬编码文本，不能将其直接解释为 13 个论文数值错误。

- 历史正文使用 P6≥15，部分分析或工具使用 ≥18；真实漏洞触发不能只由分数阈值定义。

## 3. 审稿意见对应的修改与实验

### A. 评分可信度和真实目标验证（最高优先级）

两位评审均质疑 LLM judge 的稳定性；cT21 另质疑参考档案未经人工验证、同源模型偏好和早期阶段对后期指标的混淆。

建议：

1. 人工核验全部 30 个 CVE 的厂商、产品、固件版本、漏洞二进制及预期触发信号；标记只来自公开资料、已手工重放和仍不确定的条目。不要将“参考资料有 PoC”等同于本研究已成功复现。
2. 对所有声称成功的运行重放真实目标验证。记录固件/二进制哈希、进程或仿真器证据、输入确实到达目标的证据，以及漏洞特异性信号；可行时加入良性输入或修补版对照，排除普通崩溃、模拟服务及其他漏洞。
3. 主指标使用可审计的真实目标端到端成功；六阶段分数用于诊断，Plan 单独报告。保留旧加权分作为辅助指标并做权重敏感性分析。
4. 两位专家独立、隐藏模型身份地标注分层抽样运行；建议先做 60–90 条，覆盖全部声称成功样本、simulation、部分进展和失败。报告分歧及裁决方式、类别一致率、κ 等适当统计和 judge 对真实成功判断的误报/漏报。样本量为实施建议，并非 CFP 要求。
5. 对同一批固定证据重复运行 judge，并使用不同模型家族交叉评估，报告方差、人机一致性和模型排名稳定性。固定 judge 版本、prompt 和参数。

### B. “从零开始”与环境预备的配对对照（最高优先级）

KLRF 明确要求量化 pre-/post-environment 差异。仅从低成功率推断环境重建是主因，证据不足。

建议在同一组 CVE、同一 agent/harness 和固定预算下设置：

- A：仅 CVE ID，加统一任务要求；
- B：CVE ID + 经核验的漏洞固件；
- C：CVE ID + 已启动并验证可触发的真实漏洞环境，不向 agent 提供解法或 PoC。

主要比较真实成功率、模拟替代率、成本和耗时。C 能建立的案例可能偏向容易复现的 CVE，应报告共同子集、无法建立 C 的案例及原因，避免将不同集合的成功率直接相减。既有成功子集上的条件成功率可以补充，但因各模型到达子集不同，不能独自证明后期能力的因果差异。

预算有限时，先选覆盖三类漏洞和不同 ISA 的 12–15 个案例、2 个模型、3 次重复，在完整共同子集上完成三种设置，再决定扩展范围；此规模是建议而非录用门槛。历史 A 结果只有在环境、预算、模型快照可比时才能复用。

### C. 样本选择、覆盖范围与参考正确性（高优先级）

两位评审均认为 30 个、三类均衡样本不足以代表 IoT 总体。cT21 要求 ISA、年份、固件体积和依赖复杂度等信息。

建议先补齐 696→30 的筛选数量、排除理由与完整元数据；给出厂商、设备类、年份、ISA/位数/端序、固件体积、libc、服务与依赖、模拟模式和 NVRAM/硬件约束。无法可靠测量的项目明确标为缺失。

准确描述范围为“以 CVE ID 为唯一初始实例输入，针对经整理、有公开证据及可获得固件的已知 IoT 漏洞开展复现”。这是任务输入限制与样本选择限制的区别，不应声称覆盖任意野外 CVE、未知漏洞发现或根因发现能力。

报告三类分层结果与不确定性；均衡样本不能自然推出野外总体成功率。扩充时优先覆盖新厂商、ISA 和复杂度，而非只提高总数；保留原 30 个为核心集，新增独立扩展集，并考虑对未按可获取性筛选的样本进行小规模生态有效性检查。

### D. Harness、预算与模型结论（中高优先级）

KLRF 质疑单一 OpenCode harness 和任意权重。建议选择有区分度的子集，在第二个 harness 上使用相同模型和预算复测，并检查提示词、工具集与执行预算敏感性。

固定 OpenCode commit、模型提供商/实际模型 ID/快照和日期、采样参数、镜像 digest、工具版本、架构和计费口径。正文“latest version”不足以支持复现；展示名被清理为相同名称不能证明免费路由与正式模型相同。优先报告每次独立运行的成功率及按 CVE 聚类的不确定性，另报三次尝试中至少成功一次；逐阶段取最大分拼成的曲线不是一次真实完整轨迹。

## 4. 安全会议中的研究定位与写作

建议围绕“自动化漏洞复现如何证明运行了真实漏洞目标，以及环境重建造成哪些可测量的失败”组织文章，避免只写模型排行榜。可能的研究问题：

1. 仅给 CVE 时能否实现可验证的真实目标复现？
2. 提供固件或就绪环境分别改变多少成功率、成本和模拟行为？
3. 哪些 ISA、依赖和系统约束对应主要瓶颈？
4. 实证结论在评估器、harness 和计分选择下是否稳定？

相关工作目录已有 CyberGym/E2E、CVE-Bench、SEC-bench、K-Repro、ExploitBench 等，可从任务初始输入、是否提供环境、是否运行真实目标、验证机制及覆盖范围逐项比较。全文避免无证据地声称所有既有 benchmark 都不验证真实目标。

正文安排建议：问题与安全意义、相关工作与任务边界、数据及参考验证、真实目标验证方法、实验设计、主要发现、可靠性与局限。决定贡献的验证和对照实验应进入正文，不能只依赖附录。

## 5. CFP 要求与截止时间

核对材料：本地 `../submission/USENIX Security '27 Call for Papers _ USENIX.html`；官网 2026-11-09 修订 PDF https://www.usenix.org/sites/default/files/sec27_cfp_110926.pdf；ML 投稿说明 https://www.usenix.org/conference/usenixsecurity27/submitting-ml-work-usenix-security 。本次确认的关键要求一致。

| Cycle 2 事项 | AoE 日期 | 按当日 23:59 AoE 换算北京时间 |
| --- | --- | --- |
| 强制注册 | 2027-01-19 | 2027-01-20 19:59 |
| 论文提交 | 2027-01-26 | 2027-01-27 19:59 |
| Artifact 提交 | 2027-01-29 | 2027-01-30 19:59 |

最终分钟数应以 HotCRP 公布值为准，建议按前一天作为内部截止。

- 注册时固定标题、完整作者名单和 topics，提交非空暂定摘要；登记作者 ORCID。投稿前所有作者更新 HotCRP profile 并确认 submission terms；填写真实 COI。每作者每轮最多七篇。
- 正文最多 13 页；初投参考文献和附录不限页，正文应自洽；录用终稿总计最多 20 页。用官方 letter 双栏模板，不靠负间距、删除作者块等方式挤页；图表灰度可读。
- 投稿必须有 Open Science Appendix，说明代码、数据、benchmark 等 artifacts 的访问方式或不能提供的具体理由。可选功能性/可复现性 artifact evaluation 与此强制附录并非同一要求。
- 匿名 artifact 链接写进论文，在正文截止后固定；之后三天仅用于匿名化和上传，不能改论文；宽限结束后 artifact 冻结。链接至少有效到 2027-05-18 shepherd approval 截止。
- 投稿论文及 artifact 双盲，清理作者、机构、commit history、路径及可追踪访问机制。arXiv 预印本允许存在，仍需提交匿名稿。
- Ethics Appendix 在 2027 年不强制，但强烈建议。本文适合明确已知漏洞、隔离复现、网络范围、未进行第三方未授权测试及固件再分发限制等实际措施，不能陈述尚未执行的措施。
- 建议主 topic 选 Software Security，按实际内容补充 IoT；ML 用于安全任务不应仅因使用 LLM 就选 Security of ML。此为结合官方 topic 说明的判断。
- 两份 AAAI 拒稿建议不禁止转投；提交前仍须确认正式决定或退出审稿状态。同一工作不能同时投有归档论文集的会议；若曾投 USENIX '27 Cycle 1 且被拒，不能转投 Cycle 2。当前目录未发现这种 Cycle 1 记录。
- CFP 的“No Replication submissions”指不设 replication 投稿类型，并不意味着不能研究漏洞复现任务。
- 模板当前缺少 `plainurl.bst` 的构建依赖，应在正式迁稿时补齐并验证。迁入正文前保留原始官方 ZIP 和历史版本。
